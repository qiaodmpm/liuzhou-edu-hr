# 产品方案：未使用编制补录

> 版本：v1.8 | 日期：2026-06-24 | 状态：方案确认中，暂不改代码

---

## 1. 背景与问题

### 1.1 编制名额的四种状态

一个编制批复名额，从批复到最终入编，会经历四个阶段：

```
编办批复 10 人
  │
  ├── 招聘岗位申请提交（语文 5 人）──→ 状态：已占用
  │       │                           名额被招聘岗位"预定"，不可再给别人用
  │       ├── 核减 1 人 ──→ 状态：已核减
  │       │                 名额消失，批复实际缩为 9
  │       ├── 入编 3 人 ──→ 状态：已使用
  │       │                 通过入编审批，正式在编（终态）
  │       └── 暂缓 1 人 ──→ 状态：已暂缓
  │                         已分配但推迟办理，名额冻结中
  │
  └── 未占用 5 人 ──→ 状态：可用
                      还可用于新的招聘岗位申请
```

在编制岗位台账中，一个计划记录的完整状态由四个字段共同描述：

| 字段 | 含义 | 示例 |
|------|------|------|
| `adjustedApprovedCount` | 编办批复的有效名额（原始批复 − 核减） | 9 |
| `occupiedCount` | 已被招聘岗位**占用**，尚未入编 | 5 |
| `usedCount` | 已通过入编审批，正式在编 | 3 |
| `deferredCount` | 聘用手续中暂缓办理 | 1 |

**剩余可用 = adjustedApproved − occupied − used − deferred = 9 − 5 − 3 − 1 = 0**

> **核心规则**：招聘岗位申请一旦**提交**，编制立即被占用。入编审批通过只是把"占用"转化为"使用"（occupied → used），编制总消耗不变。

### 1.1A 核心设计原则：聚合字段 100% 由计划记录计算

台账中的 `已批复计划数`、`已使用计划数`、`未使用计划数` 等字段**不是用户手动输入的**，而是从计划记录数组（`careerPlans` / `controlPlans`）自动汇总计算得出。

```
            ┌──────────────────────────────────┐
            │        careerPlans[]              │
            │  ┌────────────────────────────┐  │
            │  │ Plan A (线上 B2026-001)    │  │
            │  │   approved=5, adjusted=5   │  │
            │  │   occupied=2, used=2       │  │
            │  ├────────────────────────────┤  │
            │  │ Plan B (线下 柳编办[25]8号) │  │
            │  │   approved=3, adjusted=3   │  │
            │  │   occupied=1, used=2       │  │
            │  └────────────────────────────┘  │
            └──────────────┬───────────────────┘
                           │ 自动计算（只读）
                           ▼
            ┌──────────────────────────────────┐
            │  已批复计划数 = Σ adjusted       │
            │  已使用计划数 = Σ used           │
            │  未使用计划数 = 已批复 − 占用 − 已用 − 暂缓 │
            └──────────────────────────────────┘
```

**设计规则**：

| 规则 | 说明 |
|------|------|
| **聚合字段只读** | `careerApprovedPlan`、`careerUsedPlan` 等 UI 展示字段**不接受手动输入**，一律从 plans 数组计算 |
| **唯一写入入口** | 修改编制的唯一途径是操作计划记录（补录/编辑/删除 plan），聚合字段自动重算 |
| **线下补录仅限有效期内** | 补录线下计划时，有效期截止日必须 ≥ 当前日期。已过期的线下批复不应录入台账（历史数据可归档但不计入统计） |
| **一致性保证** | 每次渲染台账页面前调用 `syncAggregatesFromPlans()`，确保聚合字段与 plans 数组始终一致 |

> **反例**：当前编辑表单中"已批复计划数"仍是一个可手动编辑的 `<input>` 字段。这违反了"聚合字段由计划记录计算"的原则。应改为：当 plans 数组非空时，该输入框为 `readonly`，值自动从 plans 计算；当 plans 数组为空时（兼容旧数据），允许手动输入但提示"请补录计划明细"。

### 1.2 核心痛点

当前台账模型用**聚合数值**（approval − used = unused）来管理未使用编制，存在以下问题：

| 问题 | 具体表现 |
|------|---------|
| **无明细** | 只知道"总数 N 个"，不知道这 N 个分别来自哪次批复、何时到期 |
| **无追溯** | 入编时关联了编制批次，但台账侧只能做 ±1 运算，看不出哪个批次还剩多少 |
| **线下缺口** | 系统上线前已由编办线下批复的编制计划，台账中没有记录，学校无法在新系统中使用这些名额 |
| **有效期盲区** | 编制批复都有有效期（通常 1 年），聚合数值不区分到期与否，导致过期名额也可能被误用 |
| **占用不计入** | 招聘岗位申请提交后编制已被占用，但台账不知道，导致"剩余可用"计算偏高，后续申请可能超量 |
| **核减/暂缓不联动** | 聘用手续模块的核减和暂缓记录，本质上是"批复了但没用到"的编制，但这些信息不存在台账中 |

### 1.3 典型场景

```
场景 A：系统上线前已有线下批复

  2024年12月，编办线下批复柳州八中事业编 5 人（有效期至 2025-12-31）。
  2025年3月，学校通过线下流程为 3 人办理了入编。
  2025年6月，系统上线。学校建立台账时填写：
    - careerApprovedPlan = 5（含线下批复）
    - careerUsedPlan = 3（含线下入编）
    - careerUnusedPlan = 2 ← 这 2 个名额属于哪次批复？有效期是？
  
  → 系统不知道这 2 个未使用名额的来源和有效期，无法正确管理

场景 B：编制申请批复了，但聘用过程有岗位核减

  编制使用申请批复：事业编 10 人（有效期至 2026-06-30），生成计划记录 PLAN-C-001。
  招聘批次 RCB001：语文 5 人 + 数学 3 人 + 英语 2 人 = 10 人，关联编制批次 B2026-001。
  聘用手续 EMP001：关联招聘批次 RCB001，为上述 3 个岗位办理聘用。
    岗位"语文教师"：原计划 5 人 → 核减 2 人（报名不足）→ 实际计划 3 人
    岗位"数学教师"：原计划 3 人 → 核减 1 人 → 实际计划 2 人
    岗位"英语教师"：原计划 2 人 → 核减 0 → 实际计划 2 人
  聘用二审通过后，沿链路追溯：
    3 个岗位 → 招聘批次 RCB001 → 编制批次 B2026-001 → 计划记录 PLAN-C-001
    → PLAN-C-001.adjustedApprovedCount: 10 → 7（核减 2+1+0=3 人）
    → 实际有效批复数从 10 降为 7

  入编：7 人全部通过入编。
  台账现状：careerApprovedPlan=10, careerUsedPlan=7, careerUnusedPlan=3。
  
  问题修正后：careerPlans[0].approvedCount=10, 
              careerPlans[0].adjustedApprovedCount=7（核减后）,
              careerPlans[0].usedCount=7,
              careerPlans[0].remainingCount=0 ← 实际已无可用名额
              
  原先那 3 个"未使用名额"实际是核减掉了，不应再算作可用编制计划。
  台账现状：careerApprovedPlan=10, careerUsedPlan=7, careerUnusedPlan=3。
  
  问题：那 3 个核减的名额其实已经"作废"了（编办发文核减），不应再算作可用的编制计划。
  → 台账只记录了数量，没记录这 3 个名额的"核减"状态

场景 C：编制计划到期未用完

  编制使用申请批复：控制数 8 人（有效期 2025-01-01 ~ 2025-12-31）。
  实际入编：6 人。
  台账：controlApprovedPlan=8, controlUsedPlan=6, controlUnusedPlan=2。
  
  2026年1月，这 2 个未使用名额已过期，不能再用于入编。
  → 但台账的"可申请控制数"公式 `quota − actual − approved` 未考虑有效期
  
  修正公式应为：可申请 = quota − actual − approved(有效期内)
```

## 2. 编制管理 / 岗位管理 / 聘用管理 对未使用编制的关联分析

### 2.1 编制使用申请模块

| 关联点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| 表单"未使用计划数"展示 | 显示 `approved − used` 聚合值 | 应展示**有效期内**的未使用计划明细列表 |
| 表单"可申请编制数" | = `quota − actual − approved`（所有已批复） | 应扣除**已过期**的已批复计划，公式改为 `quota − actual − approved(有效)` |
| 审批通过后回写台账 | `careerApprovedPlan += 批复数` | 应**追加一条计划记录**（含来源批次、批复数、有效期起始/截止） |
| 编制池联动机制（§7） | "可用编制 = approved − used − pending" | 应精确到计划级：剩余可用名额应能定位到具体是哪个批次的剩余 |

**结论**：编制申请模块是编制批复的**源头**，每次审批通过应在台账中生成一条"编制计划记录"，而非仅做数值累加。

### 2.2 教师入编模块

| 关联点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| 关联编制批次 | 下拉选择已批复的编制使用申请批次 | 同现有逻辑，但选择后应展示**该批次的剩余名额** |
| 审批通过后回写台账 | 入编通过 → 已使用数 +N | 应执行"占用转化为使用"：对应计划记录的**占用数 −N，已使用数 +N**（总量不变，不改变剩余可用），而非单纯给已使用数加数 |
| 入编人数校验 | 校验入编人数 ≤ 批次剩余名额 | 应确保入编人数 ≤ 计划记录的**剩余可用**（= 有效批复 − 占用 − 已使用 − 暂缓） |
| 已过期批次不可选 | 有该逻辑 | 保持，且台账侧对应计划记录应标记为"已到期" |

**结论**：入编模块是编制计划的**消费者**，每次入编应关联到一条具体的计划记录，在该计划记录上扣减"剩余名额"。

### 2.3 教师出编模块

| 关联点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| 审批通过后释放名额 | `careerActual −= N`，`unused` 间接增加 | 释放的是"在编人数"，不影响已批复计划。`careerAvailable = quota − actual − approved` 中 actual 减少 → available 增加 |
| 与控制数的关系 | 控制数出编释放控制数名额 | 同理，释放的控制数名额不会自动变成新的"已批复计划"，需重新走编制申请流程 |

**结论**：出编模块不直接操作"未使用编制"，它影响的是 `careerActual`/`controlActual`，间接影响 `careerAvailable`/`controlAvailable`。不需要改变出编与计划记录的关联。

### 2.4 聘用手续模块

> **关键认知**：聘用手续直接操作的是**招聘岗位**（position），不是编制批次。核减/暂缓通过"岗位 → 招聘批次 → 编制使用申请批次 → 台账计划记录"的链路，最终联动到编制。

**数据链路**：

```
聘用手续（employ）
  │  操作对象：招聘岗位卡片（每个岗位有 planCount / cancelCount / deferredPersons）
  │  关联：employ.recruitBatchId → 招聘批次
  │
  ▼
招聘模块（recruit）
  │  关联：recruit_record.staffingBatchId → 编制使用申请批次
  │
  ▼
编制使用申请模块（staffing）
  │  关联：staffing_submission → 台账中的计划记录
  │
  ▼
编制岗位台账（org_ledger）
    目标：careerPlans[i] / controlPlans[i]
```

**各层数据关系**：

```
聘用手续 — 岗位维度:
  employ_record
    ├── recruitBatchId: "RCB20260501001"     ← 关联的招聘批次
    ├── businessType: "recruitment"
    └── formData.recruitmentForms
        └── positions: [                      ← 按岗位逐岗录入
              {
                positionName: "语文教师",
                planCount: 5,                 ← 该岗位原计划招聘数（来自招聘批次）
                cancelCount: 2,              ← 核减数
                cancelDocNo: "柳人社[2026]15号", ← 核减依据
                cancelReason: "报名人数不足",
                actualPlan: 3,               ← 实际计划 = planCount − cancelCount
                completedCount: 1,            ← 已办理
                thisCount: 1,                 ← 本次办理（花名册行数）
                deferredPersons: [{ name: "张三", reason: "体检复查" }]  ← 暂缓明细
              }
            ]

招聘批次:
  recruit_record
    ├── id: "RCB20260501001"
    ├── staffingBatchId: "B2026-001"         ← 关联的编制使用申请批次
    └── positions: [...]

编制使用申请:
  staffing_submission
    ├── id: "S20260611001"
    ├── batchId: "B2026-001"
    └── staffingType: "career"

台账计划记录:
  careerPlans[i]
    ├── sourceSubmissionId: "S20260611001"
    ├── approvedCount: 10
    ├── adjustedApprovedCount: 10 → 8 (核减后)
    └── deferredCount: 0 → 1 (暂缓后)
```

| 关联点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| 岗位核减（聘用侧） | 聘用手续中按岗位填写核减人数/依据/原因，仅影响附件4汇总表 | 核减应**沿链路联动台账**：岗位核减 → 招聘批次 → 编制申请批次 → 台账计划记录 `adjustedApprovedCount` 扣减 |
| 岗位暂缓（聘用侧） | 聘用手续中按岗位填写暂缓人员明细，仅影响附件4汇总表 | 暂缓应**沿链路联动台账**：岗位暂缓 → 台账计划记录 `deferredCount` 累加。暂缓名额仍属有效计划 |
| 附件4 招聘计划完成情况 | 按岗位逐行展示 原计划/核减数/实际计划/已办理/本次/暂缓 | 台账侧应能**汇总**各计划记录的实时状态，与聘用侧附件4 数据一致 |
| 关联招聘批次 | 聘用必选已完成的招聘批次 | 聘用→招聘→编制→台账的链路已建立，台账侧计划记录应记录该链路（用于追溯和联动） |

**结论**：聘用模块的核减/暂缓通过三级链路（岗位 → 招聘批次 → 编制批次 → 台账计划记录）最终联动到编制。核减 = 编办正式削减了已批复名额，台账计划记录的 `adjustedApprovedCount` 应减去核减数；暂缓 = 推迟办理但不取消名额，台账 `deferredCount` 累加。

### 2.5 岗位设置模块

| 关联点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| 岗位总量控制 | `totalControlQuota = careerQuota + controlQuota` | 不受计划记录影响，总量由编办核定 |
| 实有人员分类 | `postBreakdown.*.actual` 来自入编/出编 | 不入编就没有"实有"，与计划记录不在同一维度 |
| 岗位结构校验 | 各类岗位占比不超过上限 | 入职后按岗位分类统计，不直接操作计划记录 |

**结论**：岗位设置模块不直接操作"未使用编制"，它管理的是岗位分布结构。两者的交集在于：入编后，岗位的 `actual` 和计划的 `used` 同时+1。

## 2.6 三模块关系总览（编制 ← 招聘 ← 聘用）

> **核心认知**：编制、招聘、聘用是三个独立但逐层依赖的模块。核减/暂缓沿此依赖链逐层传递。

```
┌───────────────────────────────────────────────────────────────────┐
│                    编制 → 招聘 → 聘用 三层关系                       │
│                                                                   │
│  ┌─────────────────────┐                                          │
│  │   编制使用申请        │  ← 第 1 层：编办批复编制名额              │
│  │   (staffing)         │                                          │
│  │                     │  产出：编制使用申请批次 + 申请记录          │
│  │  B2026-001          │  写入台账：careerPlans[i]（计划记录）       │
│  │  ├─ S20260611001    │  关键字段：approvedCount, validStart/End   │
│  │  │   (事业编 10人)   │                                          │
│  │  └─ S20260611002    │                                          │
│  │      (控制数 5人)    │                                          │
│  └─────────┬───────────┘                                          │
│            │ 招聘批次关联编制申请批次                                 │
│            ▼                                                       │
│  ┌─────────────────────┐                                          │
│  │   招聘               │  ← 第 2 层：发布招聘岗位                  │
│  │   (recruit)          │                                          │
│  │                     │  关联：recruit.staffingBatchId             │
│  │  RCB20260501001     │  产出：招聘批次 + 各岗位招聘计划            │
│  │  ├─ 语文教师 5人     │  关键字段：positions[].planCount           │
│  │  ├─ 数学教师 3人     │                                          │
│  │  └─ 英语教师 2人     │  招聘计划数 = 编制批复数的分配             │
│  └─────────┬───────────┘  (Σ岗位.planCount ≤ 编制批复总数)         │
│            │ 聘用关联招聘批次                                        │
│            ▼                                                       │
│  ┌─────────────────────┐                                          │
│  │   聘用手续            │  ← 第 3 层：实际办理入编/核减/暂缓        │
│  │   (employ)           │                                          │
│  │                     │  关联：employ.recruitBatchId               │
│  │  EMP20260624001     │  操作对象：招聘岗位卡片                    │
│  │  ├─ 语文教师:        │                                          │
│  │  │   planCount=5    │  ← 来自招聘批次（只读）                    │
│  │  │   cancelCount=2  │  ← 聘用时核减（联动到编制计划记录）         │
│  │  │   actualPlan=3   │  ← = 5−2（自动计算）                      │
│  │  │   本次办理: 2人   │  ← 花名册人数                             │
│  │  │   暂缓: 1人       │  ← 推迟办理（联动到编制计划记录）           │
│  │  ├─ 数学教师: ...    │                                          │
│  │  └─ 英语教师: ...    │                                          │
│  └─────────────────────┘                                          │
│                                                                   │
│  ═══════════ 联动方向 ═══════════                                  │
│                                                                   │
│  【招聘占用】                                                       │
│  招聘(第2层) 岗位申请提交 ──→ 编制(第1层) 计划记录.occupiedCount += N │
│  （提交即占用，不需要等入编）                                         │
│                                                                   │
│  【入编转化】                                                       │
│  入编审批通过 ──→ 计划记录: occupiedCount−N, usedCount+N              │
│  （占用转化为使用，总消耗不变）                                        │
│                                                                   │
│  【核减/暂缓】                                                       │
│  聘用(第3层) 岗位核减 ──→ 招聘(第2层) 批次关联 ──→ 编制(第1层)      │
│                                      adjustedApproved−M, occupied−M │
│  聘用(第3层) 暂缓登记 ──→ 编制(第1层) deferredCount+P               │
│                                                                   │
│  ⚠️ 注意：联动是沿着依赖链**向上**追溯，不是聘用直接操作编制         │
└───────────────────────────────────────────────────────────────────┘
```

## 3. 跨模块数据流（现状 vs 目标）

### 3.1 现状：聚合数值模式

```
编制申请 approved → careerApprovedPlan += N（无批次追踪）
入编 approved     → careerUsedPlan    += N（无计划关联）
出编 approved     → careerActual      −= N（正确）
聘用核减          → （不联动台账）
聘用暂缓          → （不联动台账）
台账展示          → careerUnusedPlan = approved − used（聚合值，无明细/无有效期）
```

### 3.2 目标：计划级追踪模式（含占用维度）

```
编制申请 approved ──→ 台账追加计划记录:
                      { sourceSubmissionId, approvedCount, occupiedCount:0, usedCount:0,
                        validStart, validEnd, status:'active' }

═══════════════════════════════════════════════════════════════════
招聘岗位申请提交 — 【关键】编制被占用:

  ① 学校提交招聘岗位申请:
     招聘批次 RCB001，岗位"语文教师" planCount=5

  ② 沿链路:
     招聘批次 RCB001 ──→ 关联编制批次 B2026-001
     ──→ 台账 careerPlans[i].sourceBatchId = 'B2026-001'

  ③ 联动台账:
     careerPlans[i].occupiedCount += 5
     （名额被"预定"，不能再用于其他岗位申请）

  ④ 剩余计算:
     remaining = adjustedApproved − occupied − used − deferred
───────────────────────────────────────────────────────────────────

入编 approved — 【占用转化为使用】:

  ① 入编审批通过 N 人（关联编制批次 B2026-001）

  ② 联动台账:
     careerPlans[i].occupiedCount −= N  ← 释放占用
     careerPlans[i].usedCount += N       ← 转为已使用
     总消耗不变（occupied + used + deferred 不变）

  ③ 若 used + occupied + deferred == adjustedApproved → exhausted
───────────────────────────────────────────────────────────────────

出编 approved — 不操作计划记录:

  careerActual −= N（仅影响在编人数，不释放已批复名额）
───────────────────────────────────────────────────────────────────

聘用核减/暂缓 — 三级链路联动:

  ① 聘用手续二审通过，岗位级操作:
     岗位.cancelCount = M  (核减)
     岗位.deferredPersons = [{ name, reason }, ...]  (暂缓)

  ② 沿链路:
     聘用.recruitBatchId → 招聘批次 → 编制批次 → 计划记录

  ③ 联动台账:
     核减: careerPlans[i].adjustedApprovedCount −= M
           careerPlans[i].occupiedCount −= M    ← 同时释放占用
           （核减 = 名额消失，批复缩小，占用释放）
     
     暂缓: careerPlans[i].deferredCount += P
           （名额仍在，但冻结，不可用于新申请）

  ④ 汇总核算:
     remaining = adjustedApproved − occupied − used − deferred
═══════════════════════════════════════════════════════════════════

有效期到期        ──→ 系统/管理员标记: status: 'expired'
                      剩余名额不再计入聚合 approvedPlan

台账展示          ──→ careerUnusedPlan = Σ(非到期计划.remaining)
                      careerAvailable = quota − actual − Σ(非到期计划.adjustedApproved)
```

## 4. 数据模型

### 4.1 新增：编制计划记录（PlanRecord）

在台账数据结构中新增 `careerPlans` 和 `controlPlans` 数组，每条记录代表一次编制批复（线上或线下）：

```javascript
// 事业编计划记录
careerPlans: [
  {
    // ===== 计划标识 =====
    id: 'PLAN-C-20260624001',            // 计划编号 PLAN-{C|K}-{日期}{序号}
    source: 'online',                     // 'online' 线上编制申请 / 'offline' 线下批复补录
    
    // ===== 关联来源 =====
    sourceBatchId: 'B2026-001',           // 线上：关联的编制使用申请批次 ID
    sourceSubmissionId: 'S20260611001',    // 线上：关联的编制使用申请记录 ID
    // 线下补录时，以下字段由学校手动填写：
    offlineDocNo: '',                     // 线下批复文号（离线补录时必填）
    offlineApprovedBy: '',                // 线下批复机关名称（如"柳州市委编办"）
    
    // ===== 批复内容 =====
    approvedCount: 5,                     // 批复的计划使用人数（原始批复数）
    adjustedApprovedCount: 5,            // 校正后的计划数 = approvedCount − 核减数
    occupiedCount: 3,                     // 【关键】已被招聘岗位占用但未入编的人数
    usedCount: 2,                         // 已入编人数（累计入编审批通过人数，终态）
    deferredCount: 0,                     // 暂缓人数（从聘用模块同步）
    
    // ===== 计算字段 =====
    // remainingCount = adjustedApprovedCount − occupiedCount − usedCount − deferredCount
    // 含义：当前还可用于新招聘岗位申请的剩余名额
    //
    // 四个字段的关系：
    //   occupiedCount：招聘岗位申请提交 → +N（名额被"预定"，提交即占用）
    //   usedCount：    入编审批通过     → occupied−N, used+N（占用转化为使用，总量不变）
    //   deferredCount：聘用暂缓登记     → +N（名额冻结）
    //
    // 关键规则：入编不改变"总消耗"（occupied + used + deferred 不变）
    //          只有核减才释放名额（adjustedApproved 减少，occupied 对应减少）
    //          招聘岗位申请提交时必须校验：Σ岗位.planCount ≤ remainingCount
    
    // ===== 有效期 =====
    validStart: '2025-01-01',             // 编制有效期起始（YYYY-MM-DD）
    validEnd: '2025-12-31',               // 编制有效期截止（YYYY-MM-DD）
    
    // ===== 状态 =====
    status: 'active',                     // 'active' 有效 / 'exhausted' 已用完 / 
                                          // 'expired' 已到期 / 'adjusted' 已核减调整
    
    // ===== 使用类型明细（必填，精确到每个类型）=====
    useTypes: {
      // 每行五个字段：
      //   批复人数(手动) / 已占用(手动) / 已入编(手动) / 暂缓(手动) / 未使用(计算)
      // 未使用 = 批复 − 已占用 − 已入编 − 暂缓，自动计算
      publicRecruit: { approved: 3, occupied: 1, enrolled: 2, deferred: 0, unused: 0 },
      selfRecruit:   { approved: 0, occupied: 0, enrolled: 0, deferred: 0, unused: 0 },
      talentMid:     { approved: 0, occupied: 0, enrolled: 0, deferred: 0, unused: 0 },
      talentHigh:    { approved: 0, occupied: 0, enrolled: 0, deferred: 0, unused: 0 },
      transfer:      { approved: 2, occupied: 0, enrolled: 1, deferred: 1, unused: 0 },
      other:         { approved: 0, occupied: 0, enrolled: 0, deferred: 0, unused: 0 }
    },
    // 汇总校验（每行约束）：
    //   0 ≤ occupied ≤ approved
    //   0 ≤ enrolled ≤ approved − occupied
    //   0 ≤ deferred ≤ approved − occupied − enrolled
    //   unused = approved − occupied − enrolled − deferred（自动计算）
    // 跨行汇总：
    //   Σ approved  = 计划批复总数
    //   Σ occupied  = 计划的 occupiedCount
    //   Σ enrolled  = 计划的 usedCount（= 已入编人数）
    //   Σ deferred  = 计划的 deferredCount
    //   Σ unused    = 计划的 remainingCount（剩余可用）
    
    // ===== 关联聘用（核减/暂缓追溯）=====
    linkedEmployIds: [],                  // 关联的聘用手续记录 ID 列表，用于追溯核减/暂缓来源

    // ===== 元数据 =====
    createdAt: '2025-01-01',              // 记录创建时间
    createdBy: '市管理员',                // 创建人（线上=审批人，线下=补录人）
    updatedAt: '2025-06-15',              // 最后更新时间
    notes: ''                             // 备注
  }
]
```

### 4.4 聚合字段保持兼容

继续保留 `careerApprovedPlan`、`careerUsedPlan`、`careerUnusedPlan` 等聚合字段，但改为**从 plan 数组自动计算**：

```javascript
// 聚合计算（从 plans 数组汇总，仅统计非到期计划）
careerApprovedPlan  = Σ careerPlans.filter(非到期).adjustedApprovedCount
careerOccupiedPlan  = Σ careerPlans.filter(非到期).occupiedCount
careerUsedPlan      = Σ careerPlans.filter(非到期).usedCount
careerDeferredPlan  = Σ careerPlans.filter(非到期).deferredCount

// 已到期计划不参与上述任何聚合。
// 如需要历史累计值（含到期），从全部 plans 单独计算，不在台账主页展示。

// 未使用 = 批复有效 − 已占用 − 已入编 − 暂缓
careerUnusedPlan    = careerApprovedPlan - careerOccupiedPlan - careerUsedPlan - careerDeferredPlan

// 可申请编制数：还可向编办申请多少新名额
careerAvailable     = careerQuota - careerActual - careerApprovedPlan
```

**注意**：
- `careerUnusedPlan` 公式与 v1.1 不同。v1.1 中 `未使用 = 已批复 − 已使用`，忽略了占用和暂缓维度。v1.4 公式扣除了全部四个维度。
- **已到期计划完全排除**：已到期计划的任何数据（批复、占用、已用、暂缓、剩余）均不计入台账聚合值。台账展示当前有效数据，历史累计可单独查看。

## 5. 补录流程设计

### 5.1 触发时机

学校在**首次建立台账**或**台账被退回修改**时，系统检测到计划记录数组（`careerPlans` / `controlPlans`）为空或不完整，提示学校补录。

触发条件：计划明细合计（非到期计划的批复数之和）小于台账的已批复计划数。即存在差额，说明有线下批复未登记。

```javascript
// 触发条件（以事业编为例）
var plansSum = Σ careerPlans.filter(非到期).adjustedApprovedCount;
var needBackfill = plansSum < ledger.careerApprovedPlan;
```

```
│     → 已入编填 2                                   │
│                                                    │
│  规则：0 ≤ 已入编 ≤ 批复 − 已占用                   │
│                                                    │
│                                          [ 知道了 ] │
└────────────────────────────────────────────────────┘

┌─ 暂缓人数 ⓘ ──────────────────────────────────────┐
│                                                    │
│  已确定具体人选，但因故暂时无法办理入编的人数。       │
│  常见原因：体检复查中、原单位离职未办完等。           │
│  名额被冻结，待条件满足后再办入编。                   │
│                                                    │
│  📋 举例：批复 3 人，1 人体检未完成                 │
│     → 暂缓填 1                                     │
│                                                    │
│  ⚠️ 同一人不能同时出现在"已入编"和"暂缓"中。        │
│  规则：0 ≤ 暂缓 ≤ 批复 − 占用 − 入编                │
│                                                    │
│                                          [ 知道了 ] │
└────────────────────────────────────────────────────┘

┌─ 未使用(算) ⓘ ────────────────────────────────────┐
│                                                    │
│  系统自动计算：批复 − 占用 − 入编 − 暂缓             │
│  该类型下还能用于新招聘申请的剩余名额。               │
│                                                    │
│  不可手动修改，随前四列变化实时更新。                 │
│                                                    │
│                                          [ 知道了 ] │
└────────────────────────────────────────────────────┘
```

**四个输入字段的关系**（角标浮层之上，顶部提示条简要概括）：

```
批复 5 人 ──┬── 已占用 1 人  ← 招聘途中，名额被预订
            ├── 已入编 3 人  ← 已经落地，变为在编人员
            ├── 暂缓   1 人  ← 定人了但卡住了，名额冻结
            └── 未使用 0 人  ← 剩下的（自动算）

每行约束：批复 ≥ 占用 + 入编 + 暂缓
```

### 5.4 补录校验规则

| 校验项 | 规则 | 失败提示 |
|--------|------|---------|
| 批复文号 | 必填，不可与已有计划重复 | "请填写批复文号" / "该文号已存在" |
| 批复机关 | 必填 | "请填写批复机关" |
| 有效期起始 | 必填 | "请选择有效期起始" |
| 有效期截止 | 必填，截止 ≥ 起始 | "截止日期不能早于起始日期" |
| **有效期必须在有效期内** | `validEnd ≥ today` | "该计划已到期（截止日期：YYYY-MM-DD），不可补录。已到期的编制计划请联系管理员归档处理" |
| **使用类型分布必填** | 六种类型每行至少填写批复人数，**批复合计必须 > 0** | "使用类型分布为必填项，请填写各类型的批复人数" |
| 每行批复人数 | ≥ 0，整数 | — |
| 每行已占用人数 | 0 ≤ 已占用 ≤ 该行批复人数 | "第 N 行已占用人数（X）超过该行批复人数（Y）" |
| 每行暂缓人数 | 0 ≤ 暂缓 ≤ 该行批复人数 − 该行已占用 | "第 N 行暂缓人数（X）超过该行可用数（Y）" |
| 批复合计 | 六行批复人数之和 = 自动显示的批复合计 | （自动计算，用户不可直接输入合计） |
| 计划合计一致性 | 全部计划 adjustedApprovedCount 之和 = 台账已批复计划数 | （自动同步，不单独校验） |

> **补录有效期规则**：线下补录仅接受有效期截止日 ≥ 当前日期的计划。已到期的线下批复不应录入台账——台账是当前时点的快照，到期名额已不具备法律效力。
>
> **使用类型必填规则**：使用类型分布不再是可选项。每条计划记录都必须明确每个使用类型的批复人数、占用人数和暂缓人数。这样可以追溯到具体是哪个招聘类型的名额被占用或暂缓了，便于后续联动。

### 5.5 补录后的数据一致性

补录完成后，系统自动调用 `syncAggregatesFromPlans()` 重算聚合字段。由于聚合字段 100% 从 plans 数组计算，**不存在手动输入不一致的可能**。

```
Σ(all careerPlans.adjustedApprovedCount) → careerApprovedPlan（自动同步，无需校验）
Σ(all careerPlans.usedCount) → careerUsedPlan（自动同步）
Σ(all careerPlans.occupiedCount) → careerOccupiedPlan（自动同步）

每次渲染页面 / 保存台账 / 提交审核前，均自动执行 syncAggregatesFromPlans()。
用户不可手动修改聚合字段，因此不会出现"聚合值 ≠ plans 合计"的情况。
```

## 6. 状态与有效期管理

### 6.1 计划记录状态流转

```
                    ┌───────────────────────┐
                    │       active           │  正常有效
                    │  剩余可用 > 0 且未到期  │
                    │  (adjusted − occupied  │
                    │   − used − deferred    │
                    │       > 0)             │
                    └──────┬─────┬──────────┘
                           │     │
    总消耗 == adjusted     │     │  validEnd < today
    (occupied+used+        │     │  且剩余 > 0
     deferred == adjusted) │     │
                           ▼     ▼
       ┌───────────┐    ┌───────────┐
       │ exhausted │    │  expired   │
       │  已用完    │    │  已到期    │
       └───────────┘    └───────────┘
       
       核减调整（聘用模块联动）:
       active ──→ adjusted（批复缩小，但未用完）
         │
         └── 如果占用 + 已使用 + 暂缓 == 调整后批复 → exhausted

       到期时仍有在途业务:
       active/occupied ──→ expired（到期）
         │ 此时显示警告"该计划已到期，仍有 N 人占用中 / M 人暂缓中"
         │ 不自动释放占用或暂缓，由管理员人工判断处理
```

### 6.2 状态判定规则

| 状态 | 判定条件 | 前端展示 | 招聘可占用？ | 入编可选？ |
|------|---------|---------|:--:|:--:|
| `active` | `adjustedApproved − occupied − used − deferred > 0` 且 `validEnd ≥ today` | 绿色"有效" | ✅ | ✅ |
| `exhausted` | `adjustedApproved − occupied − used − deferred === 0` | 灰色"已用完" | ❌ | ❌ |
| `expired` | `validEnd < today` 且仍有剩余 | 红色"已到期" | ❌ | ❌ |
| `adjusted` | 已核减调整，仍有剩余 | 橙色"已调整" | ✅ | ✅ |

> **注意**：exhausted 的判断条件是 `adjustedApproved − occupied − used − deferred === 0`，即**四个维度**全部算入总消耗，而非仅 `adjustedApproved === used`。

### 6.3 即将到期提醒

当计划记录满足以下条件时，在台账页展示提醒：

```
条件：validEnd − today ≤ 60天 且 remainingCount > 0

提醒文案：
⚠️ 计划「柳编办[2025]8号」剩余 2 个名额，将于 60 天内到期，请尽快安排招聘或申请延期
```

## 7. 与现有模块的对接规则

### 7.1 编制使用申请模块（staffing-*）

**申请表单读取**：

| 当前 | 目标 |
|------|------|
| 读取 `careerApprovedPlan` 聚合值展示"已批复计划数" | 读取 `careerPlans`，仅汇总 `active` 状态，展示"已批复计划数（有效）" |
| 读取 `careerUnusedPlan` 聚合值展示"未使用计划数" | 读取 `careerPlans`，汇总各计划剩余名额，点击可展开明细 |
| 读取 `careerAvailable` 展示"可申请编制数" | 公式不变，但 `careerApprovedPlan` 使用有效计划汇总值 |

**审批通过后写入**：

| 当前 | 目标 |
|------|------|
| `careerApprovedPlan += 批复数` | 追加一条 `careerPlans` 记录（source='online'） + 重新计算聚合值 |

### 7.1A 招聘模块（recruit-*）— 【关键】岗位申请提交 → 占用编制

**招聘岗位申请提交时**：

| 当前 | 目标 |
|------|------|
| 提交后不联动台账 | 沿"招聘批次 → 编制批次 → 计划记录"链路，`occupiedCount += 岗位申请人数` |

**校验规则**：

| 校验项 | 规则 | 失败提示 |
|--------|------|---------|
| 岗位申请数 ≤ 计划剩余 | Σ 岗位.planCount ≤ Σ careerPlans[i].remainingCount（关联的编制批次剩余名额） | "岗位申请人数（N）超出编制批复剩余名额（M）" |
| 编制有效期 | 关联的编制批次有效期 ≥ 当前日期 | "编制批次已到期，不可申请" |

**招聘岗位申请审核通过后**：不额外联动台账（提交时已占用），仅建立招聘→编制关联桥接供后续聘用追溯。

**招聘岗位核减/取消时**：

| 操作 | 联动 |
|------|------|
| 招聘侧核减岗位计划数 | 等效于释放占用：`occupiedCount −= 核减数`，`adjustedApprovedCount −= 核减数` |
| 招聘侧取消整个岗位 | `occupiedCount −= 岗位原计划数` |

> **核心规则**：招聘岗位申请**提交即占用**，不需要等审核通过。因为一旦提交，学校就无法再把这个名额用于其他岗位。

### 7.2 教师入编模块（entry-*）

**编制批次选择**：

| 当前 | 目标 |
|------|------|
| 下拉选择已批复的编制使用申请批次 | 同现有逻辑，但额外展示每个批次的剩余名额 |
| 校验入编人数 ≤ 批次审批总数 | 修正为：入编人数 ≤ 计划记录的 `remainingCount` |

**审批通过后写入**：

| 当前 | 目标 |
|------|------|
| `careerUsedPlan += 入编人数` | **占用转化为使用**：扣减对应计划记录的 `occupiedCount`，增加 `usedCount`（总消耗 occupied+used 不变）+ 重新计算聚合值 |

### 7.3 聘用手续模块（employ-*）

#### 7.3.1 核减/暂缓联动台账的完整链路

聘用手续核减的是**招聘岗位**，通过三级链路联动到编制计划记录：

```
┌─────────────────────────────────────────────────────────────────────┐
│                        核减/暂缓联动链路                              │
│                                                                     │
│  聘用手续（employ）                                                   │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 招聘岗位卡片（逐岗位录入）                                      │   │
│  │                                                              │   │
│  │ 岗位：语文教师                                                 │   │
│  │   原计划招聘数 (planCount) ............ 5 人 （来自招聘批次）    │   │
│  │   核减数     (cancelCount) ........... 2 人 ← 当前操作        │   │
│  │   核减依据   (cancelDocNo) ........... "柳人社[2026]15号"     │   │
│  │   核减原因   (cancelReason) .......... "报名人数不足"          │   │
│  │   实际计划   (actualPlan) ............ 3 人 （=5−2，自动计算） │   │
│  │                                                              │   │
│  │   暂缓人员   (deferredPersons) ....... [{name:"张三",         │   │
│  │                reason:"体检复查中"}]    ← 当前操作            │   │
│  │                                                              │   │
│  │ employ.recruitBatchId = "RCB20260501001"                     │   │
│  └──────────────────────┬──────────────────────────────────────┘   │
│                         │ 关联                                     │
│                         ▼                                          │
│  招聘模块（recruit）                                                 │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ recruit_record                                              │   │
│  │   id: "RCB20260501001"                                      │   │
│  │   staffingBatchId: "B2026-001"  ← 关联编制使用申请批次        │   │
│  │   status: "completed"                                       │   │
│  └──────────────────────┬──────────────────────────────────────┘   │
│                         │ 关联                                     │
│                         ▼                                          │
│  编制使用申请模块（staffing）                                         │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ staffing_submission                                         │   │
│  │   id: "S20260611001"                                        │   │
│  │   batchId: "B2026-001"                                      │   │
│  │   school: "柳州市第八中学"                                     │   │
│  │   staffingType: "career"  (事业编)                            │   │
│  │   status: "approved"                                        │   │
│  └──────────────────────┬──────────────────────────────────────┘   │
│                         │ 关联                                     │

│  编制岗位台账（org_ledger）                                           │

│  │ careerPlans[i]                                              │   │
│  │   sourceSubmissionId: "S20260611001" ← 匹配到！               │   │

│  │   adjustedApprovedCount: 10 → 8  ← 核减 2 人                 │   │
```

#### 7.3.2 多岗位汇总核减

一次聘用手续可能涉及**多个招聘岗位**，每个岗位独立核减，但可能指向**同一条编制计划记录**（如果这些岗位都来自同一编制使用申请批次）：

```
聘用手续（一次性办理 3 个岗位的聘用）:

岗位A（语文教师）: planCount=5, cancelCount=2 → 实际计划 3
岗位B（数学教师）: planCount=3, cancelCount=1 → 实际计划 2
岗位C（英语教师）: planCount=2, cancelCount=0 → 实际计划 2

三者都关联 recruitBatchId = "RCB20260501001"
  → recruit_record.staffingBatchId = "B2026-001"
  → staffing_submission.id = "S20260611001"
  → 台账 careerPlans[0].sourceSubmissionId = "S20260611001"

汇总核减:
  careerPlans[0].adjustedApprovedCount -= (2 + 1 + 0) = 3
  careerPlans[0].notes += "聘用核减: 语文教师2人、数学教师1人"
```

**特殊情况**：若不同岗位分属不同的编制使用申请批次（招聘批次关联了多个编制批次），则需分别联动到各自的计划记录：

```
岗位A → recruitBatchId → staffingBatchId A → careerPlans[0]（核减 2）
岗位D → recruitBatchId → staffingBatchId B → careerPlans[1]（核减 1）
```

#### 7.3.3 联动时机

| 事件 | 联动动作 | 影响字段 |
|------|---------|---------|
| **招聘岗位申请提交** | 沿链路找到台账计划记录，`occupiedCount += 岗位申请人数` | `occupiedCount +N` |
| **聘用手续二审通过**（核减） | 读取所有岗位的 cancelCount，沿链路找到台账计划记录，`adjustedApprovedCount −= M`，`occupiedCount −= M` | `adjustedApproved −M`, `occupied −M` |
| **聘用手续二审通过**（暂缓） | 读取所有岗位的 deferredPersons，沿链路找到台账计划记录，`deferredCount += P` | `deferredCount +P` |
| **入编审批通过** | 沿链路找到台账计划记录，`occupiedCount −= N`，`usedCount += N` | `occupied −N`, `used +N` |
| **聘用手续二审驳回后重提** | 核减/暂缓数据**反向恢复**后再重新联动（先加回，重审后重新扣） | 恢复原值 |
| **招聘批次被删除** | 聘用记录保留副本，台账计划记录标注"关联批次已删除" | — |
| **编制申请记录被删除** | 阻止删除（有下游关联）或标记为 orphan | — |

> **关键规则**：核减同时扣减 `adjustedApprovedCount` 和 `occupiedCount`。因为核减的岗位名额本就是占用的一部分——核减 = "这个名额不招了"，所以批复缩小的同时，占用也释放。

#### 7.3.4 联动校验规则

| 校验项 | 规则 | 失败提示 |
|--------|------|---------|
| 链路完整性 | 聘用.recruitBatchId → 招聘记录存在 → 招聘.staffingBatchId → 编制申请存在 → 台账计划记录存在 | "无法定位到编制计划记录，请检查招聘批次和编制申请的关联" |
| 核减数不超 | Σ岗位.cancelCount ≤ careerPlans[i].adjustedApprovedCount（当前有效批复数） | "核减总数（N）超过已批复计划可用数（M）" |
| 暂缓不超 | Σ岗位.deferredPersons.length ≤ careerPlans[i].remainingCount（核减后） | "暂缓人数（N）超过剩余可用名额（M）" |
| 核减+暂缓合理性 | 核减后剩余 ≥ 已办理 + 本次办理 + 暂缓 | "实际计划不足以覆盖已办理+本次+暂缓" |
| 核减依据必填 | cancelCount > 0 时 cancelDocNo 必填 | "核减人数>0，请填写核减依据文号" |

#### 7.3.5 聘用侧不直接操作台账

**重要约束**：聘用手续模块**不直接读写**台账数据。联动逻辑统一在台账侧执行：

```
聘用二审通过
  → 更新 employ_record.status = 'completed'
  → 调用 window.dispatchEvent(new CustomEvent('employ:completed', { detail: employ_record }))
  → 台账侧监听该事件
  → 台账侧执行核减/暂缓联动（读取 employ_record → 追踪链路 → 更新 plan 记录）
  → 台账侧重新计算聚合值
```

这样保持模块间的松耦合，聘用模块不需要知道台账的数据结构。

### 7.4 岗位设置模块（post-*）

不需要改动。岗位设置管理的是岗位结构分布，与编制计划记录处于不同维度。

## 9. 边界情况

### 9.1 全部计划都在线上（无需补录）

如果学校所有的已批复计划都来自线上编制使用申请，系统自动从 `staffing_submissions` 中生成 `careerPlans` 记录，不触发补录提示。

### 9.2 部分线上 + 部分线下

系统自动为线上记录生成计划记录，差额部分提示学校补录。

### 9.3 台账建立后新增线上批复

后续编制使用申请审批通过后，自动在台账中追加一条计划记录。不需学校手动操作。

### 9.4 补录时有效期已过 → 拒绝补录

学校补录线下计划时，若填写的有效期截止日早于当前日期，系统**拒绝补录**并提示"该计划已到期（截止日期：YYYY-MM-DD），不可补录。已到期的编制计划请联系管理员归档处理"。

**理由**：台账是当前时点的快照，一份已经过期的批复不具备法律效力，录入台账只会让数据变脏。如需保留历史记录，应有独立的"历史归档"功能（不在此方案范围内）。

### 9.5 补录后审批人校正

区/市管理员审核台账时，可以编辑或删除学校的补录计划记录（校正）。校正后需要填写校正原因。

### 9.6 计划记录与入编/聘用的交叉引用

- 入编时关联了某条计划记录（通过编制批次），入编通过后自动扣减该计划记录
- 聘用核减联动时，需通过招聘批次 → 编制批次 → 计划记录的链路找到对应记录
- 如果计划记录被手动删除，而存在关联的入编记录 → 阻止删除，提示"该计划已有入编关联，不可删除"
- 如果计划记录已过期但仍有剩余名额 → 标记为过期，入编下拉不可选

### 9.7 核减/暂缓联动链路断裂

聘用→招聘→编制的三级链路中任一级断裂时的处理：

| 断裂场景 | 台账侧处理 |
|---------|-----------|
| 聘用关联的招聘批次被删除 | 保留核减/暂缓数据在聘用侧，台账侧计划记录标注"关联批次已删除"，不再联动 |
| 招聘批次存在但关联的编制批次被删除 | 台账计划记录标记为 orphan，核减/暂缓数据写入 notes 但不对应具体计划 |
| 编制申请记录存在但台账侧对应计划记录被手动删除 | 阻止删除计划记录，提示"该计划有聘用联动记录（N 条），请先处理聘用侧数据" |
| 招聘批次未关联编制批次（招聘独立创建） | 核减/暂缓仅影响招聘侧统计数据，台账计划记录不受影响（无链路可追溯） |

### 9.8 同一编制计划被多次聘用引用

一个编制计划可能被**多次聘用**（分批办理聘用手续）：

```
计划 PLAN-C-001: approvedCount=10
  第一次聘用（2026-03）：语文教师 planCount=5, cancelCount=1 → adjusted=9
  第二次聘用（2026-06）：数学教师 planCount=3, cancelCount=0 → adjusted=9（无变化）
  第三次聘用（2026-09）：英语教师 planCount=2, cancelCount=1 → adjusted=8

每次聘用二审通过时，台账计划记录 accumulated:
  - 累计核减 = 1+0+1 = 2
  - adjustedApprovedCount = 10 − 2 = 8
  - notes 记录每次核减的来源（聘用编号 + 岗位 + 核减数）
```

### 9.9 计划到期时仍有在途占用或暂缓

当一条计划记录的编制有效期到期（`validEnd < today`），但其 `occupiedCount > 0`（招聘在途）或 `deferredCount > 0`（人员暂缓）时：

| 情况 | 处理方式 |
|------|---------|
| 占用 > 0（招聘在途） | 台账页显示警告"该计划已到期，仍有 N 人占用中，请核实招聘进度"。**不自动释放占用**——系统无法判断这些占用是否合法 |
| 暂缓 > 0（人员推迟） | 同上，显示警告"该计划已到期，仍有 N 人暂缓中"。不自动取消暂缓 |
| 占用 = 0 且 暂缓 = 0 | 正常标记到期，无额外提示 |

> **原则**：到期不自动释放任何名额。占用和暂缓可能涉及正在进行的线下流程，自动释放会导致数据错乱。统一交给管理员人工核实处理。

### 9.10 管理员校正计划记录的权限

区/市管理员审核台账时，可以校正计划记录。校正范围按记录来源区分：

| 操作 | 线上计划（source='online'） | 线下计划（source='offline'） |
|------|:--:|:--:|
| 编辑批复人数 | ❌ 不可（由编制申请模块联动） | ✅ 可（需填校正原因） |
| 编辑已使用人数 | ❌ 不可（由入编模块联动） | ✅ 可（需填校正原因） |
| 编辑占用人数 | ❌ 不可（由招聘模块联动） | ✅ 可（需填校正原因） |
| 编辑暂缓人数 | ❌ 不可（由聘用模块联动） | ✅ 可（需填校正原因） |
| 编辑有效期 | ❌ 不可 | ✅ 可（需填校正原因） |
| 删除整条记录 | ❌ 不可（有下游关联） | ✅ 可（仅限占用=0、已使用=0、暂缓=0、无聘用关联，需填删除原因） |

> **原则**：线上计划的字段由各业务模块自动联动，管理员不可手动修改。线下补录的计划允许管理员校正，但所有校正操作均需填写校正原因，记录到变更日志中。

### 10.2 数据迁移

对于已有台账数据，首次加载时执行迁移：

```javascript
function migrateToPlanRecords(ledger) {
  // 如果已有 careerPlans 数组，跳过
  if (ledger.careerPlans && ledger.careerPlans.length > 0) return ledger;
  
  // 尝试从 staffing_submissions 中提取线上记录
  const submissions = JSON.parse(localStorage.getItem('staffing_submissions') || '[]');
  const schoolSubs = submissions.filter(s => 
    s.school === ledger.schoolName && s.status === 'approved'
  );
  
  ledger.careerPlans = schoolSubs
    .filter(s => s.staffingType === 'career')
    .map(s => ({
      id: 'PLAN-C-' + s.id,
      source: 'online',
      sourceBatchId: s.batchId,
      sourceSubmissionId: s.id,
      approvedCount: s.finalApprovedCount || s.totalStaff,
      adjustedApprovedCount: s.finalApprovedCount || s.totalStaff,
      occupiedCount: 0, // 无法从现有数据推算，保守为 0
      usedCount: 0, // 无法从现有数据推算，保守为 0
      deferredCount: 0,
      validStart: s.validStart || '',
      validEnd: s.validEnd || '',
      status: 'active',
      useTypes: { /* 从 s.useForms 映射 */ },
      createdAt: s.approveDate || s.submitDate,
      createdBy: '系统迁移',
      updatedAt: ledger.updatedAt,
      notes: '从编制使用申请记录自动迁移'
    }));
  
  // 计算线上已覆盖的批复数
  const onlineTotal = ledger.careerPlans.reduce((sum, p) => sum + p.adjustedApprovedCount, 0);
  
  // 差额 = 台账的已批复计划数 − 线上计划数之和
  // 若存在差额，标记为"待补录"
  if (onlineTotal < ledger.careerApprovedPlan) {
    ledger._pendingBackfill = {
      career: ledger.careerApprovedPlan - onlineTotal,
      control: ledger.controlApprovedPlan - /* 同理计算 */ 0
    };
  }
  
  // 同理处理 controlPlans...
  
  return ledger;
}
```

## 11. 总结

### 核心思路

用"计划记录明细"替代"聚合数值"来管理已批复的编制计划，实现：

1. **可追溯**：每个编制计划有来源、文号、有效期、四个维度的使用情况
2. **可补录**：学校可录入线下已批复但系统中不存在的计划
3. **可联动**：编制申请创建计划 → 招聘占用计划 → 入编转化占用为使用 → 聘用核减/暂缓校正
4. **可管控**：有效期管理、到期提醒、状态流转，剩余可用精确到四个维度

### 编制名额的四种状态

```
剩余可用 = 有效批复 − 招聘占用 − 已入编 − 暂缓
              ↑          ↑        ↑      ↑
           (核减后)   (提交即占) (终态) (冻结)
```

**关键规则**：招聘岗位申请提交即占用，入编审批通过只是占用→使用的转化，总消耗不变。

### 关键设计决策

| 决策 | 方案 | 理由 |
|------|------|------|
| 聚合字段保留 | ✅ 从数组 100% 自动计算 | 禁止手动输入，唯一入口是操作计划记录 |
| 补录有效期限制 | ✅ 仅接受有效期内的线下计划 | 台账是当前时点快照，到期名额不具备法律效力 |
| 到期计划排除 | ✅ 不参与任何聚合统计 | 保持台账数据洁净，历史数据可单独查看 |
| 补录时机 | 台账建立/编辑时，检测到差额触发 | 不影响正常流程，仅在需要时出现 |
| 计划状态 | 4 种状态（有效 / 已用完 / 已到期 / 已核减） | 覆盖全部生命周期 |
| 招聘占用 | 提交即占，入编转化 | 招聘提交后编制不可复用，避免超额 |
| 核减联动 | 扣减批复 + 释放占用 | 核减 = 批复缩小 + 占用释放 |
| 暂缓联动 | 聘用二审通过时标记暂缓数 | 暂缓不是核减，名额冻结但未消失 |
| 管理员校正 | 仅限线下计划，需填原因 | 线上计划由系统联动，不可手动改 |
